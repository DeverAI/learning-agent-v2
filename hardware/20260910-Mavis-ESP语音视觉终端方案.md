## 0.1 使用场景（2026-09-10 补充，**优先级最高**）

| 事实 | 影响 |
|------|------|
| **学校不给带手机** | Android APK 在校内**完全不可用**。这台设备是校内**唯一的 学习Agent 终端**，不是"锦上添花" |
| **学校大概给带这台设备**（待确认口径） | 需求真实存在。但"能带"≠"能用"，必须拆开看 |
| 用户初三，2027 年中考 | 时间是比钱稀缺得多的资源 |

### 场景拆解：「能带」≠「能用」

校内真正能用的时间窗很窄，必须先想清楚：

| 场合 | 可行性 | 障碍 |
|------|--------|------|
| 上课中 | **不成立** | 你在听课，且屏幕亮起、声音外放会打扰课堂 |
| 自习课 / 晚自习 | **受限** | 举着带屏设备拍照+出声，在教室里极度显眼，易被当成玩电子产品 |
| 课间 | **太短** | 10 分钟内完成"拍题→等结果→看讲解"不现实 |
| 宿舍（若住校） | **可行** | 最现实的主力窗口 |
| 周末在家 | **无增量** | 有手机和电脑，设备没有额外价值 |

**结论：如果答案落在「基本没法用」，边际效应依然接近零——只是原因从"手机够用"换成了"校内无处可用"。**

### 场景反向决定交互方式（重要）

**校内以静音为主，外放基本不成立。** 这会推翻本方案原先对音频能力的优先级：

| 原假设 | 校内实际情况 | 修正 |
|--------|--------------|------|
| 扬声器外放播报讲解 | 教室/自习室不能外放 | **耳机为主**（3.5mm / 蓝牙） |
| 双麦 + AEC 免耳机对讲 | 用耳机时 AEC 价值大幅下降 | **AEC 从"必需"降为"加分"** |
| 语音提问是主要输入 | 教室说话同样不便 | **触屏输入权重上升 → 屏幕与触屏成为第一优先** |

**推论：若校内是主场，S3-Touch-LCD-3.5-C（单麦、¥200-240）就基本够用，不必为 AEC 多花 ¥200 上 P4-4.3-C。** 省下的钱更该花在屏幕观感与耳机上。

见 §1-P3 的相应修正。

## 1. 最终审查：13 个问题

这是本方案最该先读的部分。按严重度排序，前 5 条会直接影响选型。

### 严重（影响选型，必须处理）

**P1. v2 的首选自相矛盾——必须推翻**

v2 把「微雪 ESP32-S3-CAM-OV5640 裸板」排第 1，但那是**裸板 + 独立屏 + 独立壳**的组合。**三件分开买、还要固定在一体，通用外壳基本做不到，最后必然回到 3D 打印或热熔胶——与「不要我 3D 打印」直接冲突。**

**修正：只要要求上屏，首选就必须是「带屏 + 带壳」的整机型号。** 见 §4。

**P2. 「小」和「屏」此消彼长，必须选一个**

| 形态 | 尺寸量级 | 屏幕够不够用 |
|------|----------|--------------|
| 裸板 37×37mm | 极小 | 无屏 |
| 带屏带壳整机（3.5"/4.3"） | 约 100×65×20mm | 够：取景 + 显示讲解 |
| 2" 带屏裸板 | 约 60×45mm | 勉强：320×240 取景尚可，读讲解偏挤 |

**结论：屏幕小于 2 寸就没有意义**（读不了讲解、取景框太小）。接受「小」在这次意味着「掌心级、能放桌面」，而不是「口袋里」。**若坚持口袋级，只能放弃屏幕。**

**P3. 音频能力有隐藏落差——最容易踩的坑**

同样「有麦克风有扬声器」，差别很大：

| 板卡 | 麦克风 | 回声消除 | 后果 |
|------|--------|----------|------|
| **微雪 ESP32-S3-Touch-LCD-3.5-C** | **单麦** | **无** | 扬声器外放时无法边放边听，只能「按一下说一句」 |
| 微雪 ESP32-S3-CAM-OV5640（裸板） | 双麦阵列 (ES7210) | **有** | 免耳机可对讲，但无屏无壳 |
| **微雪 ESP32-P4-WIFI6-Touch-LCD-4.3-C** | **双麦 (ES8311+ES7210)** | **有** | **屏壳音频全齐，唯一全满足的** |

**这是本次审查最重要的发现**：带壳带屏的 3.5-C 音频最弱（单麦无 AEC）。**如果想要「像正常对话一样」的体验（不用按按钮、外放时也能听清你说话），必须选双麦 + ES7210 + AEC 的型号，也就是 P4-4.3-C。**

> **修正（见 §0.1）**：本条按「外放对话」场景成立。但**校内场景以耳机 + 静音为主，外放对话不成立，AEC 的价值随之大幅下降**。若校内是主场，本条的优先级下调，3.5-C 够用。

**P4. ESP32-S3 同时驱动「屏 + 5MP 相机 + 音频 + WiFi」有资源瓶颈**

ESP32-S3 的 PSRAM 带宽和 DMA 通道是共享资源。QSPI 屏刷新、DVP 摄像头出图、I2S 音频收发、WiFi 收发四件事并发时，容易出现**屏撕裂、拍照掉帧、录音丢采样**。

**ESP32-P4 没有这个瓶颈**：原生 MIPI-CSI（不走并口）、独立媒体引擎、硬件 H.264 编码、32MB PSRAM。

**修正 v2 结论：如果确定要「屏 + 相机 + 音频」同时工作，P4 是更稳的选择，不只是「更强」。**

**P5. 拍题取景是体验命门，也是最容易被漏掉的工作量**

- **有预览**：摄像头需持续低分辨率出图 → 占用带宽与功耗，S3 上可能与屏刷新打架
- **无预览盲拍**：对着题目按一下就拍，**拍歪概率极高**，尤其在手持、光线不均时
- **可行解**：屏幕跑 QVGA（320×240）预览流 + 按快门时切 1600×1200 静态抓帧；屏上画取景框提示对齐。实现「双分辨率切换」是 P1-P2 阶段的主要工作量，**要排进计划，不要当成顺手就有的功能。**

### 中等（影响体验，需提前对齐预期）

**P6. 网络——已解除（2026-09-10 用户确认）**

- **客户端隔离风险解除**：服务端是独立机器，设备可正常连通。原 P6.1 / P7 作废。
- **剩余小项**：ESP32-S3 **只支持 2.4G**，校园网 2.4G 通常拥挤；ESP32-P4 + C6 支持 **WiFi 6 含 5GHz**，此项体验更好。不是阻塞项，但仍是选 P4 的一个加分理由。
- 少数校园网有并发设备数上限或 MAC 报备要求，量级小，遇到再说。

**P8. v1 不要承诺「实时打断」**

路线二不做 WebSocket 流式音频的话，交互只能「录一段 → 传一段 → 等回复」，即**按一下说一句**。这与小智那种自然对话有明显落差。
**建议：v1 明确不做打断，验收标准定为「按住说话，松开 3 秒内开始播报」。** 否则会因为预期错位而觉得「做失败了」。

**P9. 价格水分大，别按最低价做预算**

同一块 3.5-C，不同渠道报价：微雪官方 $25.99-32.99（**当前显示 Out of Stock**）／OpenELAB €29.95 含税／另一渠道 €35.95／AUD$42.94／某店标 $67.93。
**国内到手价务必按具体店铺 + 具体 SKU 核实。**

**P10. 锂电的物理安全**

裸板 + 裸 3.7V 锂电没有保护壳，放书包有挤压、短路、鼓包风险。整机带壳（3.5-C / 4.3-C）能缓解；裸板方案务必配电池盒或选带壳版本。

### 轻微（工程细节，届时处理）

**P11. 5MP JPEG 上传延迟**：2592×1944 约 1-2MB。建议设备端降到 1600×1200（约 150-300KB）再传。服务端单文件 10MB 不是瓶颈，延迟才是。

**P12. 两套设备的隐含成本**：e-ink + 语音终端 = 两套固件、两套配网、两套 OTA。共用 `/api/device/snapshot` 能省一半服务端工作，但设备端仍是两份代码。**建议明确 e-ink 是「稍后」还是「并行」。**

**P13. 屏幕总成重量与结构**：3.5" 整机约 82g（含壳），加电池后约 100-120g，靠 FPC 与排针连接，摔落易损。桌面放置为主，不要指望随身折腾。

## 2. 拍题场景下的摄像头红线

拍题和「能看到东西」是两回事。**视场角和焦距比像素数更关键**：

- 视场角太窄 → 拍不全整页；太广（>100°）→ 纸面桶形畸变，边缘文字被拉开，OCR 与视觉模型都掉点
- 焦距太短 → 近距离透视变形严重
- **68° 左右是拍 A4 纸最舒服的区间**（接近人眼单眼视野，畸变可控）

| 传感器 | 像素 | 最大分辨率 | 焦距 | 光圈 | 视场角 | 拍 A4 题目的判断 |
|--------|------|------------|------|------|--------|------------------|
| **OV5640** | **5MP** | **2592×1944** | 4.1mm | F2.8 | **D:68° H:55° V:42°** | **最适合**——畸变小、像素足 |
| OV3660（DFR1154） | 3MP | 2048×1536 | 3.2mm | F2.4 | **D:160°** | **不适合**，纸面边缘明显变形 |
| OV5647（P4-4.3-C 配套） | 5MP | 2592×1944 | — | — | MIPI CSI | 可用 |
| GC2145 | 2MP | 1616×1232 | 2.38mm | F2.4 | D:68° | 可用但像素紧 |
| GC0308 | 0.3MP | 648×488 | 2.5mm | F2.4 | D:58° | **不可用**，糊成一团 |

**结论：锁 OV5640 / OV5647（同为 5MP 级）。**

推论：**DFRobot DFR1154 出局**——160° 超广角与拍题天然冲突（详见 §5）。

## 3. 平台选择：ESP32-S3 vs ESP32-P4

本轮挖出乐鑫 2025 年的 ESP32-P4 + ESP-VISION，对上屏后的场景是代际提升。

| | ESP32-S3 | ESP32-P4 |
|---|---|---|
| 内核 | Xtensa LX7 双核 240MHz | **RISC-V 双核 360-400MHz + FPU + AI 指令扩展** |
| 内存 | 8MB PSRAM / 16MB Flash | **32MB PSRAM / 16MB Flash** |
| 摄像头接口 | DVP 并口（与屏争带宽） | **原生 MIPI-CSI**（不与屏争） |
| 视频编码 | 无硬件编码 | **硬件 H.264 1080p@30fps** |
| 无线 | 内置 **2.4G only** | 需配 ESP32-C6（板载），提供 **WiFi 6 含 5GHz** |
| 边缘视觉 | 需自己写 C 驱动 | **ESP-VISION 官方低代码框架，Python API，可跑 YOLO** |
| 生态成熟度 | 极高，资料海量 | 新（2025 起），例程少、SDK 版本坑多 |

**结合 P4 与 P6.2：P4 额外解决了「校园网 2.4G 拥挤」和「屏相机争带宽」两个实际问题。**

**风险要讲清楚**：P4 生态新，ESP-VISION 对 ESP-IDF 版本敏感，踩坑概率明显高于 S3。**定位是「自己动手探索」的话这个风险是收益；想尽快跑通就选 S3。**

## 5. DFRobot DFR1154 专项（按用户要求调研）

**结论：板子做得好，但设计目标与拍题冲突。**

**硬规格（已核实）**

- ESP32-S3R8，16MB Flash，SD 卡槽
- 摄像头：**OV3660 2MP（2048×1536），160° 超广角红外**，可见光 + 940nm，F2.0±5%，畸变 <8%，EFL 0.95
- 音频：**板载 I2S PDM 麦克风 + MAX98357 功放 + SPK MX1.25-2P 扬声器接口**
- 其他：LTR-308 环境光、红外补光灯（IO47）、HM6245 电源芯片
- 供电：3.3V 工作 / Type-C 5V / VIN 5-12V
- 尺寸：**42×42mm，30g**
- **包装：主板（含摄像头）×1 + 扬声器 ×1 + Gravity-4P 线 ×1**
- **无外壳、无屏、无电池、单麦无 AEC**
- 价格：$18.90（3+ $18.50 / 5+ $18.00 / 10+ $17.50），约 ¥135

**生态（它最强的地方）**

- 教程覆盖：摄像头配置、视频传输、录音 → Edge Impulse 边缘识别、OpenCV 轮廓检测、YOLO
- **提供 OpenAI 图像问答 demo 代码**，以及 **OpenAI 实时通信（RTC）的 ESP-IDF 示例仓库**
- 官方 HomeAssistant 集成教程；官方小智固件适配教程（用户走路线二，用不上）
- 支持 Edge Impulse 自定义模型训练

**为什么拍题出局**

1. **160° 超广角是决定性劣势**：拍 A4 纸明显桶形畸变（官方标 <8%，对纸面 OCR 已是硬伤），必须裁切中心区，等效像素再缩水
2. **2MP vs 5MP**：像素少 60%，看题面小字更吃力
3. **单麦无回声消除**：远场唤醒与免耳机对讲吃力
4. **无屏无壳**：加屏就要自己解决选型与装配

**反过来选它的场合**：要做**夜视/暗光**（红外补光 940nm，微雪 OV5640 没有）；要**官方级中文文档与现成 ESP-IDF 例程**少踩坑；要做**边缘视觉**（YOLO / Edge Impulse）而非拍题。

**一句话：DFR1154 是「AI 摄像头模块」，不是「拍题摄像头」。它的目标是监控/门铃/车牌，广角对它是优点；你的目标是拍 A4 纸，广角是缺点。**

## 6. 软件路线（路线二定稿）

### 6.1 关于「小智都来了我还玩啥」

**小智是管道，学习Agent 是业务闭环。**

小智给的是唤醒、聊天、查天气、控家居——一条通用输入输出链路。而学习Agent 有拍题录入、题目质疑与证据分级、组卷、知识点树、搜题批改、专注模式的分段讲解 + 检查点 + 虚拟海马体 + 黑板板书。**小智一个都没有，也不可能通用地做出来，因为它的后端不是你的知识树。**

所以：**管道层（ASR/TTS）复用成熟方案不是瞎搞，是正常工程判断**；**真正属于你的增量在管道后面**——设备固件、通信协议、把设备变成「学习Agent 的物理入口」那一层。小智做不了这件事，理由充分。代价是 ASR 必须自己接。

### 6.2 ASR：两条现成路径（路线二的关键缺口）

服务端目前**无 ASR 端点**（全靠浏览器 Web Speech API）。

**路径 A：本地 FunASR（建议先试）**

`funasr-server` 是 **OpenAI 兼容的 drop-in 替代**：

```bash
pip install -U funasr funasr-server
funasr-server --model sensevoice --device cuda   # 监听 localhost:8000
```

- 暴露 `POST /v1/audio/transcriptions` 与 `GET /v1/models`
- **现有代码只改 base_url 即可切换**
- 完全本地：零 API 成本、音频不出本机、无速率限制

**路径 B：小米 MiMo 云 ASR（与现有 TTS 同栈）**

- 模型 **`mimo-v2.5-asr`**，Token Plan 全档位套餐可用
- 计费：**按音频时长**（精确到秒，按小时统计），**30M Credits / 小时**
- **`mimo-v2.5` 多模态模型原生支持音频输入**（`input_audio`，URL 与 Base64 均可）——**FUTURE.md 第 0 条的能力层面悬念就此关闭**，剩下只是实际调用验证
- 语音合成：`mimo-v2.5-tts` / `-voiceclone` / `-voicedesign` 三款，**当前限时免费**

| | 路径 A（FunASR 本地） | 路径 B（MiMo 云） |
|---|---|---|
| 成本 | 零 API 成本，需本机算力 | 30M Credits/小时音频 |
| 隐私 | 不出本机 | 上传云端 |
| 接入 | 极低（OpenAI 兼容） | 低（已有 MiMo Key） |
| 依赖 | 新引入一个组件 | 与现有 TTS 同栈 |

**建议：先上路径 A 跑通端到端，识别质量或延迟不满意再切路径 B。** 两条接口形态接近，做成可切换 provider。

### 6.3 数据流

```
[ESP32 设备]                        [你的服务端]                 [模型层]
 麦克风 -> 录音(PCM/Opus)  --WiFi-->  /api/device/asr  --HTTP--> FunASR 本地 或 MiMo 云
                                     /api/chat         --HTTP--> LLM
 扬声器 <- 播放音频        <--HTTP--  /api/tts          --HTTP--> MiMo TTS
 摄像头 -> 抓帧 JPEG      -->         /search/upload    --HTTP--> 视觉模型(OCR/搜题)
 屏幕   <- 取景/内容显示
```

**设备端只做：采集、上传、播放、显示。零业务逻辑。**（对齐 e-ink 方案的 `/api/board/snapshot` 思路）

### 6.4 服务端待补接口（本轮不实现，登记备查）

| 接口 | 用途 | 备注 |
|------|------|------|
| `POST /api/device/asr` | 音频 → 文本 | 转发 FunASR 或 MiMo ASR |
| `GET /api/device/snapshot` | 设备首页数据 | **e-ink 与语音终端共用** |
| `POST /api/device/chat` | 设备精简对话 | 复用 `/api/chat` 内核 |
| 设备级 token | 鉴权隔离 | 现为全局 Bearer 密码，设备不应复用主密码 |

**复用现成、无需改动**：`POST /api/tts`、`POST /search/upload` + `/search/match`、`POST /ocr/*`、`POST /api/chat`。
