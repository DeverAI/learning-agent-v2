## 2. 修掉的真实缺陷

### 2.1 两个分支从来不可达（死分支）

`edit_paper` / `delete_paper` 在 round 60 就被加进了代码，有实现、有注释，
但**既不在分类器 prompt 里、也不在 `STEP_LABELS` 里** ——
分类器永远吐不出这两个 type，所以这两个分支**从来没有执行过一次**。

这类问题不会报错、不会告警、没有测试覆盖，只能靠"发现同一件事被写在三个地方"来定位。

**修法**：`agent_core.build_intent_prompt()` 由 `REGISTRY` 生成，`step_labels()` 同理。
改一处不可能漏改另一处。

**实测确认可达**（`backups/_probe_intent_routing.py`，9/9 命中）：

| 用户消息 | 分类器 type | 结果 |
|---|---|---|
| 把这份卷子的标题改成期中测试 | `edit_paper` | 命中（历史上不可能出现） |
| 删掉试卷 abc123 | `delete_paper` | 命中（历史上不可能出现） |

### 2.2 `edit_paper` 注释声称有确认闸，实际没有

原代码注释写着「沿用确认闸」，但 `edit_paper` 分支**没有任何确认检查**。
一旦它因为 2.1 的修复变可达，就等于开放了一条"分类器误判即可直接改试卷字段"的写路径。
已按注释声明的意图补上 `requires_confirm="确认修改试卷"`。

### 2.3 确认闸建在 LLM 输出上（安全管理失效）

`delete_paper` 原先读 `c.data["confirm"]` 判断是否已确认。`data` 是分类器产出的，实测分类器对
「删掉试卷 abc123」直接返回：

```json
{"paper_id": "abc123", "confirm": true}
```

**用户没有说过任何确认语，删除就会执行。** 同一批工具里
`add_question` / `edit_question` / `create_note` / `modify_note` 用的是另一套机制
（检查**用户原话**里有没有确认语），所以问题只出在 `delete_paper` 这一个上，更不容易被发现。
**这条是"实跑一次分类器看它返回什么"才发现的，只读代码看不出来。**

**修法**：授权判断只基于用户原始输入。`delete_paper` 改用 `Tool.requires_confirm="确认删除试卷"`，
分发器拿 `req.message` 原文比对；`data` 只用来传参。

### 2.4 联网检索"无法自证"（差点做成假实现）

第一版 `web_search` 实测返回 `ok: true`，但模型正文写着「由于我无法直接联网搜索信息…」。
若据此断定"联网是假的"，是**错的**；若把这段文字标成"联网检索结果"给用户，是**在骗人**。

实测数据（`backups/_probe_zhipu_ws.py`）：

| 请求 | prompt_tokens | 响应顶层 `web_search` |
|---|---|---|
| 不带 `tools` | **22** | 无 |
| `web_search.enable=true` | **2249** | 无 |
| `web_search.enable=true, search_result=true` | 2249 | **有（检索原文）** |

**结论**：联网**确实发生**（22 → 2249 就是检索结果被注入 prompt 的证据），
但**只有加 `search_result: true` 才能自证**，而模型的措辞会骗人。

**修法**（`ai_service.glm_web_search`）：
- 固定带 `search_result: true`；
- 拿不到 `web_search` 字段就**抛异常**，绝不返回正文；
- 处理器把**检索到的原文**一并呈现，并对模型的自相矛盾套话加一句说明（**不删改模型输出**），
  让"到底联没联网"由原始材料本身说话。

## 3. 新增的 4 个内容工具

设计要点：每个来源必须给出**可区分**的状态，这是项目「容量诚实」原则的直接落地。

```
ok        取到了内容
no_match  来源有数据，但没有匹配这条主题的
empty     来源本身就是空的（例如知识点图谱还没建立任何节点）
error     检索过程抛错，并带上原因
```

| 工具 | 数据来源 | 复用的现成实现 |
|---|---|---|
| `related_content` | 题库 + 笔记 + 知识点图谱 + 学习记忆（四源聚合） | `paper_service._search_questions_for_worksheet` / `._search_notes` / `knowledge_graph._load_graph` `search_graph` / `hippocampus_service.get_teaching_context` |
| `knowledge_lookup` | 知识点图谱（search / related / detail 三种模式） | `knowledge_graph.search_graph` / `get_related_nodes` |
| `recall_memory` | 海马体学习记录（掌握度 / 薄弱点 / 时长 / 最近学习） | `hippocampus_service.get_teaching_context` |
| `web_search` | 外部联网 | `ai_service.glm_web_search`（新增，见 2.4） |

**实测（`backups/_probe_content_tools.py`）**：
- 主题「勾股定理」：四源状态正确区分；
- 主题「xyzzy不存在的主题」：题库/笔记/图谱给 `no_match`，记忆给 `no_match` —— **不是** `empty`；
- 本地 `storage/knowledge_graph.json` **确实不存在** → 图谱给 `empty` 并明说"不是没查到，是图谱本身是空的"。

### 3.1 `knowledge_lookup` 的诚实性约束

知识点图谱**只有** 8 种关系（`related / is_a / part_of / created_by / contemporary / influenced / belongs_to / compared_with`），
**没有**「前置知识 / 后继知识」这类先后语义。
所以处理器在输出关联网络后固定追加一句：图谱不记录学习先后，无法从它推出学习顺序。
不因为用户问"学这个之前要会什么"就顺着编一个顺序出来。

## 4. 我自己引入、又自己拦下的风险

### 4.1 差点给所有写盘路径加上硬取消

抽注册表时我给 `Tool` 默认 `timeout=120`，并在分发处套了 `asyncio.wait_for`。
但 `wait_for` 超时是**硬取消**，会在写文件 / 写 DB 中途抛 `CancelledError`，留下半条数据 ——
而本项目明确要求取消用**协作式**（检查点 + 标志位，见 `Agent双端架构设计.md` §5.3）。

**原代码根本没有这个超时，是我"顺手加护栏"加出来的。**
已改为 `timeout` 默认 **0 = 不设超时**，只有处理器自己写成可安全中断的工具才显式开启。

### 4.2 部署脚本静默跑完

`_deploy_r11.ps1` 的 `Invoke-Ssh` 函数里既 `Write-Output` 打印远端输出、又 `return` 退出码。
PowerShell 把函数内所有输出一起当返回值，于是 B/C/D 三段的远端输出**完全没出现在屏幕上**。
改成只用 `Write-Host` + `$script:lastSshExit`。已记入 FreqErr。

## 5. 前端展示（`agent.html`）

后端 4 个工具各自在 `action.data` 里给出结构化结果，前端新增 `renderRichAction(action, container)`
把它们画成卡片，而不是让用户从一大段 Markdown 里找：

| 卡片 | 呈现 |
|---|---|
| `related_content` | 4 个来源状态色块（已取到 / 无匹配 / 来源为空 / 检索失败）+ 每源可折叠明细 |
| `web_search` | 命中的网页以**可点链接**列出（成功）；失败时红框写明失败原因 |
| `knowledge_lookup` | 匹配知识点标签；图谱为空时明说"不是没查到，是图谱里还没有任何节点" |
| `recall_memory` | 每个主题一条掌握度进度条 + 薄弱点 |

设计约束遵守情况：无 emoji；无箭头符号；**所有颜色走 CSS 变量**
（`var(--ok/--warn/--err/--accent/--border/--card-bg/--bg/--text2/--text3)`，浅色深色各自生效）。

**验证方式**：按 FreqErr 的教训，**不是**静态剥离 Jinja 标签，而是用真实 Jinja 环境渲染
`agent.html` 后抽取 7 个内联 `<script>` 块逐个 `node --check`（全部 OK）；
再用真实的 `action` 载荷配最小 DOM 桩实跑 `renderRichAction`（`backups/_probe_render_action.js`）：
9 个用例全部不抛错，并专项断言 XSS 防护与越界值处理 ——

- `javascript:` 伪协议链接被拦（`href="javascript:` 不出现在产物里）
- 标题里的 `<img src=x onerror=...>` 被转义而不是注入
- 掌握度 `3.7` 被钳到 `100%`、`0.42` 正确渲染为 `42%`
- 未知 `action.type` 与 `null` 被静默忽略（不抛错）
