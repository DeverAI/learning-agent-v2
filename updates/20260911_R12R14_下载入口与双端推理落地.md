## 2. 锁拆分（R13）——双端实时的前置

原先**整会话一把锁**：`session_chat` 一进函数就持锁，持到 AI 回答结束。
后果就是用户说的「不要一个并发死磕到底不然用户会看到卡死」——一次长对话把所有相关操作都堵住。

新增 `services/session_locks.py`，拆成三把：

| 锁 | 粒度 | 覆盖范围 |
|----|------|----------|
| `fg_lock(sid)` | 会话 | **只**串行同一会话的两条前台消息 |
| `file_lock(sid)` | 会话 | **只**覆盖会话 JSON 读改写的短临界区 |
| `bg_lock(task_id)` | 任务 | 后台任务自身的状态更新 |

配套改动：
- `delete_session` / `rename_session` **不再等待**在跑的回合 —— 等待就是卡死。
  改为立刻 409 并说明原因。不并行改的理由是"回合结束会整体回写会话 JSON，
  期间的标题改动会被**静默回滚**（丢失更新）"，与其悄悄丢，不如明确说。
- `_save(guard_deleted=True)`：回合进行中会话被删除时**拒绝回写**，
  避免"删了又回来"（比丢数据更让人困惑）。

测试：`backend/test_r13_background.py` 之前的 `backend/test_r12_locks.py`（11 条）。
其中一条测试是我**写错了前提**才发现的：锁表是弱引用，`fg_lock(sid)` 单纯调一下、
丢掉返回值等于什么都没留下 —— 已把这条语义本身写成测试钉住。

## 3. 双端推理 + 备课（R14）

### 3.1 后台推理端 `services/background_agent.py`

| 能力 | 实现 |
|---|---|
| 任务落库 | 复用 R11 建的 `AgentTask` 表 |
| 执行循环 | `RUNNERS` 注册表 + `asyncio` 任务，并发上限 5（设计文档 §5.2） |
| 协作式取消 | `Checkpoint.tick()` 在检查点查标志位，被取消抛 `TaskCancelled` |
| **兜底硬杀** | 取消后 `CANCEL_GRACE_SECONDS=25` 仍未停则强杀 —— **见 §4，这是实测逼出来的** |
| 续跑 | `cancelled`/`error` 可清标志重入队；已产出部分**不清空** |
| 重启对账 | `reconcile_on_startup()` 把残留的 `running` 标成 `error` |

重启对账不是洁癖：不做的后果是"服务重启 -> 任务行还是 running -> 前端永远显示进行中 ->
用户一直等一个**永远不会结束**的任务，且看不到任何错误"。

### 3.2 课稿 `services/lesson_service.py` + `Lesson` 表（P7）

需求逐条落点：

| 需求原话 | 落点 |
|---|---|
| 「产出**可编辑课稿**」 | `sections` 是有序切片列表，`update_section()` 可单独改一片，不必整篇重生成 |
| 「**任何需要讲解相关内容的 AI 都可以查看、切片、读取**」 | 唯一契约 `slice_lesson()`，永远带 `total_sections` / `truncated` / `used_chars`；HTTP 端点与 Agent 工具**共用同一个实现**，不出两份读法 |
| 「**全自动生成，人决定怎么走**」 | 生成在后台跑；`status` 只有 draft/final，自动产物永远先进 draft |
| 「**服务器长期存储，用户不删就不删**」 | 无 TTL、无自动清理，只有显式 DELETE |
| 「触发有两条：显式开始备课 / Agent 调用工具」 | `POST /api/lessons`（显式）与 `prepare_lesson` 工具（Agent 调用） |

**两个防"取消后一片空白"的设计**：
1. **先建骨架再逐片填**：先生成全部小标题写进 `sections`（`script` 为空），再一片片填讲解词、每片落库。
   任何时刻取消，课稿都是**可读的**：标题全在、已写的在、没写的明确为空。
2. 写不出来的分片**明确留空并记日志**，不塞占位文字冒充"写好了"。

### 3.3 前台工具与前端

新增 4 个工具（总数 23 -> **27**）：`prepare_lesson` / `list_lessons` / `read_lesson` / `edit_lesson`。

`prepare_lesson` 是**双端架构的第一个真实用户**：前台**立刻返回**（只建骨架 + 起任务），
生成丢后台。实测 `POST /api/lessons` 耗时 < 5s（不含生成）。

前端 `agent.html` 新增：
- 后台任务卡片：状态、进度条、最近步骤、**取消**按钮、**接着做**按钮；
- 取消按钮旁的说明**如实写**"会在下一个检查点停下，已写好的内容会保留"，
  不让用户以为点了立刻停；
- 课稿列表卡片（含分片完成度）。

## 4. 本轮实测到的缺陷（含我自己引入的）

| # | 缺陷 | 怎么发现的 |
|---|---|---|
| 1 | **取消形同虚设**：请求取消后任务跑了 **120 秒**仍停在 running | 探针实测。根因是"一次模型调用内部没有检查点"。修法：加 25 秒兜底硬杀 + 如实告知 |
| 2 | **进度恒为 0**：写了 `set_total()` 却从没调用 | 同一次探针。字段、接口、进度条全都写好了，**只看代码发现不了** |
| 3 | 兜底硬杀把更有价值的失败原因**覆盖**成泛泛一句 | 自查（写完立刻发现顺序错）。加 `_set_state_if_not_terminal` |
| 4 | 下载页写死版本号，与实际文件不符 | 用户要下载入口时才查出来 |
| 5 | `gradlew.bat` 在含中文路径下报 ClassNotFoundException（jar 完好） | 构建 APK 时踩到 |
| 6 | **步骤状态谎报**：界面显示「写第 1 片 已完成 / 进度 75%」，而那片讲解词一个字都没写 | **生产环境 E2E 实测**。`tick()` 的语义是"这一步开始了"，却写死 `status: "done"` |
| 7 | **一步能拖死整节课**：单片模型调用 **超过 200 秒**未返回；且撞 token 上限后还会**重试一次**，延迟翻倍 | 同一次生产 E2E |

已全部录入 `FreqErr.md`（144 -> **158 条**）。

**第 6、7 条是"生产环境真的跑一遍"才暴露的** —— 本地探针用 2 片、请求模型跑得也快，两条都看不出来。
这印证了一条经验：**探针要打在真实环境上**，本地绿过的路径不代表生产可行。

## 7. R17：备课写不出内容 —— 根因是我自己造成的

### 根因（打原始 API 实测，不是推断）

本项目主力模型 `deepseek-v4-pro` 是**推理模型**：先产出 `reasoning_content`（思考），再产出 `content`（正文）。
同一个备课 prompt 的实测：

| max_tokens | finish_reason | reasoning_tokens | 正文长度 |
|---|---|---|---|
| 2048（R15 我改的值） | `length` | 2048（吃满） | **0** |
| 8192 | `stop` | 3336 | **1404** ✓ |

**写 1500 字的课稿，光"想"就要 3300+ tokens。** 预算给小了，正文一个 token 都轮不到。

**而这个 2048 是我 R15 调出来的**：当时按"6000 字正文太长会撞上限"的**直觉**从 4096 下调到 2048 ——
方向完全反了。撞上限的是 reasoning，不是正文。

### 修复

| 改动 | 位置 |
|---|---|
| 单片预算 2048 -> **8192** | `lesson_service.SECTION_MAX_TOKENS` |
| 空正文重试**至少跳到 8192**，不再只 `×2` | `ai_service.REASONING_SAFE_MIN` + `_call` |
| 空正文日志带上 `completion_tokens` / `reasoning_tokens` | `ai_service._call` |
| 回归测试改为按真实阈值断言 | `test_delivery_regressions.py` |

最后一条值得单说：既有的 `test_empty_reasoning_response_retries_with_larger_budget`
断言写成 `calls == [128, 512]`，等于把 **"512 就够"** 这个**已被实测推翻的假设固化成契约**。
后果是我把预算调小的时候**测试全绿**，生产上一片课稿都写不出来 —— 测试保护了错误的东西。
现在 mock 改成"预算 < `REASONING_SAFE_MIN` 就拿不到正文"，这类退化会被拦住。

### 生产验证（修复后重跑同一条 E2E）

```
最终任务状态 = done   进度 = 100
output = {"total_sections": 2, "filled_now": 2, "empty_sections": 0}
课稿：total=2 已写=2 空=0
  #0 '勾股定理核心模型梳理'  1501 字
  #1 '收尾实测易错题讲评'    1097 字
VERDICT = 备课能写出内容
```

### 那两条"疑似编码 bug"的结论订正

- `UnicodeEncodeError: 'gbk' codec can't encode character '\xb2'` —— **是我的诊断探针自己的 bug**：
  我把 `print(...)` 写在了 `try:` 块内，stdout 是 GBK，打印模型回复（含 `²`）时我自己的 print 抛错，
  被 except 记到了 `deepseek_chat` 头上。已推翻并录入 FreqErr。
- `logger` 标准流切 UTF-8 仍保留，但**明确标注为"防丢日志"而非"修致命 bug"**：
  实测确认 GBK stdout 下 logging 会静默吞掉消息但**不会抛异常**。

## 8. ⚠️ 关于"撑过初三知识补漏 + 自招"的关键发现：**系统里没有内容**

2026-09-12 实测服务器与本地两边的数据家底（只读）：

| 项 | 服务器（你实际用的） | 本地开发机 |
|---|---|---|
| 题库 questions | **1**（一道初二测试题，已锁定） | 5（1 道 done，1 道有答案，**0 道有知识点标签**） |
| 笔记 notes | **0** | 2 |
| 试卷 papers | **0** | 0 |
| 批改 corrections | **0** | 0 |
| 课稿 lessons | **0** | 0 |
| 知识图谱 `knowledge_graph.json` | **文件不存在** | **文件不存在** |
| 知识树 `knowledge_tree.json` | **0 节点** | 7 节点 / 6 边 |
| 学习记忆 `hippocampus/profile.json` | **文件不存在** | **文件不存在** |
| 会话文件 sessions | **0** | 2 |

**结论（直说）**：
1. **服务器上所有基于题库 / 笔记 / 知识点图谱 / 学习记忆的功能都在空转。**
   答题、组卷、找相关内容、薄弱点复习 —— 全都没有输入。
2. **`hippocampus/profile.json` 在服务器上不存在**，意味着**专注模式 / 讲题从来没有在服务器上产生过学习记录**。
   换句话说：这套东西目前还没有被真正用来学习过一次。
3. **知识图谱文件根本不存在** → "知识补漏"缺骨架：
   补漏要回答的第一个问题是"我这个知识点不会，该先补哪个前置"，现在没有图可以回答。
4. 这**不是代码问题，是数据与闭环问题**。继续加功能只会让空壳更大。

**因此优先级应该是**：
- **A（已做）** 修掉会阻断一切生成的空正文 bug —— 否则任何 AI 产出都是空的；
- **B（下一个真正的瓶颈）** 把内容灌进来：你的错题照片 / 真题 / 课本 —— 系统已有 OCR 批量上传管线，
  缺的是材料和你走一遍真实流程；
- **C** 建立"今天该补什么"的闭环：把 `错题 -> 知识点 -> 掌握度 -> 复习清单` 串起来，
  现在每一环都有零件但没串成一条线。这是"撑过初三"最实际的东西。

**一句提醒**：`hippocampus` 的掌握度是**按遗忘曲线衰减后的估计值**，不是实测分数（R7 才把伪造值改成真实来源）。
拿它驱动复习时要清楚它的精度，别把它当成"我数学 82 分"。

### 一处需要说明的取舍

后台任务的兜底硬杀用的是 `Task.cancel()`。设计文档把它定为"卡死在非检查点 I/O 时超时强杀"的兜底，
本次落实为 25 秒。硬杀理论上仍可能落在写库中途（SQLAlchemy 会回滚事务，但**我没有构造出这种时序**），
所以这一条属于"按设计做了、但未被针对性验证"——如果后续发现半条数据，优先查这里。
