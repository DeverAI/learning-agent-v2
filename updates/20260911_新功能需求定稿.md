## 1. 备课（可编辑课稿）

| # | 问题 | 用户原话 | 落定 |
|---|------|----------|------|
| 1 | 产物形态 | **「可编辑课稿」** | **产出是一份可编辑的课稿**（不是"只存要点让 AI 现场发挥"）。需支持人工编辑 |
| 2 | 颗粒度 | **「按用户要求」** | 不预设粒度——**由用户每次指定**（可"一节课"，也可"一个知识点"） |
| 3 | 喂给谁 | **「任何需要讲解相关内容的AI都可以查看、切片、读取」** | **课稿是共享的、可被任意讲解类 AI 消费的知识资产**。关键要求有三个动词：**查看 / 切片 / 读取**——即不只是整体加载，还要支持**按片段取用** |
| 4 | 人工介入方式 | **「全自动，人决定怎么走」** | **生成过程全自动**；人的作用在**决定方向与走向**，不在逐步确认。即"AI 自己写完，人只决定往哪走" |
| 5 | 触发方式 | **「显式开始备课 / Agent 调用工具」** | **两条入口**：① 用户显式点"开始备课" ② **Agent 通过工具调用触发**（→ 需要把"备课"注册进工具表，见 §5） |

**由 #3 + #4 推出的设计要求**：
- 课稿需要**结构化存储**（可切片 = 有稳定的片段边界与引用方式），而不是一整块 Markdown
- 需要**统一的读取契约**，让"任何讲解类 AI"都能拿（Web 的 `lecture`/`focus`、桌面端 `lecture_engine`/`classroom_coach`）
- 全自动生成 + 人决定方向 → 需要"方向/大纲"与"内容"分离：**人改方向，AI 重生成内容**

## 3. 临时上课

**用户原话**：「临时上课就类似于**网课AI发现没讲清楚直接给你暂停开始讲解**一个意思」

**落定**：临时上课 **= 把桌面端 `classroom_coach` 已有的"发现讲错/跳步就暂停补讲"能力，扩展成"可主动开一段完整讲解"**。

- 语义上**不是新建课程**，而是**从当前上下文里即时起讲**（与用户先前那句「临时上课本质就是 AI 讲题的加强版」一致）
- 已有的现成基建：`InterruptEngine`（打断决策 + 五级闸门）、`ClassroomCoach`（局部卡片 + 流式讲解词 + TTS）、`lecture_engine`（拉题 → 计划 → 逐步播放）
- **缺的是**：从"补一小段"升级到"起一节课"所需的**多段连讲 + 可中断 + 可追问**（这三项目前只有 `lecture_engine` 具备，但它是题目驱动、非上下文驱动）

## 4. 双端实时（前模型 / 后模型）

**用户原话**：
> 「双端我的意思是**不要一个并发死磕到底不然用户会看到卡死**，我的意思是**前端模型拿着后端模型的产出给你讲解，同时安排后续内容让后端模型推理得到结果再拿过来**，**用户不能管理后端模型但可以让前端模型不用思考哪个方向**」

**落定（这是本次最关键的一条，且纠正了我先前对"两端"的理解）**：

| 要素 | 定稿 |
|------|------|
| **要解决的问题** | **不要"一个并发死磕到底"** —— 单一任务长跑会让用户看到卡死。必须把"面向用户的响应"与"耗时推理"分开 |
| **前模型职责** | ① 拿着**后模型的产出**给用户讲解（面向用户的唯一接口）② **同时安排后续内容**交给后模型推理 ③ 把后模型回来的结果再接过来讲 |
| **后模型职责** | 跑**后续内容的推理**，产出交给前模型 |
| **用户与后模型的关系** | **用户不能直接管理后模型**（无直接操作面） |
| **用户的控制方式** | **可以让前模型"不用思考哪个方向"** —— 即把"决定方向"这件事从前模型卸掉（交给后模型/既定计划） |

**与已有方案的关系**：这套与 `Agent双端架构设计.md` 高度同构（前台交互端 / 后台推理端 / 前台自主判断打断），**但有一处需要改设计**：
- 原方案里前台自己也有"意图分类 + 决定调用哪个工具"的职责
- 用户此条要求**前台可以"不用思考哪个方向"** → 即前台可退化为**纯播报/承接**角色，方向由后模型或既定计划给
- → 实现时需支持**前模型在两种模式间可切换**：① 自主判断（原方案）② 不思考方向、纯承接后模型产出

## 6. Web 端黑板 / 白板的边界

**用户原话**：「**Web端因为不可能在你看视频的时候讲课所以天然黑板白板**」

**我的解读**：桌面端之所以需要"把某块区域填充成黑/白"，是因为它**浮在网课视频之上**——需要遮挡/衬托底层画面。而 **Web 端不存在"在你看视频时讲课"这个场景**，它的板书区**本身就是独立的板面**，没有需要遮挡的底层内容。

→ **落定：Web 端不需要新增 `fill`/`mask` 之类的"涂黑遮罩"op。** 桌面端的 `paint_rect`（任意色填充 + 置顶覆盖）继续服务"浮在视频上"的场景。

> ⚠ 此条是我的解读，**若理解有偏差请纠正**：另一种读法是"Web 端天然就是黑板白板，所以也该有填充能力"。我采用了前一种（不需要加），因为它与"因为不可能在看视频时讲课"这个因果从句一致。

## 7. 遗留待确认（仅 1 项）

**"提前录好"的"录"到底指什么？** 三种可能，用户尚未指明：
- (a) 预生成**完整音频**（省实时 TTS 的等待，代价是存储大）
- (b) 预生成**讲解词**（播放时才合成 TTS）
- (c) **录屏 / 录播**（含板书动画）

三者对存储、生成耗时、播放器、以及"可编辑课稿"的关系都不同：
- 若是 (b)，"录好的"**就是课稿本身**（§1 的产物），两件事合一
- 若是 (a)/(c)，则需要额外的媒体资产管线（而"长期存储、用户不删就不删"这条约束正是为它准备的）
