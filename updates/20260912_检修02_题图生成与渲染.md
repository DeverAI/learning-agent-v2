### 缺陷 A（最重，已修）：消毒器把 `style` 整条删掉 → **图上的线全部不可见**

坐标推理 / 折线示意这两条路径产出的线段与圆，**笔画全部写在 `style` 里**：

```html
<line x1="40" y1="270" x2="360" y2="30" style="stroke:#333;stroke-width:2;fill:none"/>
```

而 `_sanitize_svg` 的属性白名单里**没有 `style`**，于是被整条删除。`_write_svg` 又是统一落盘口、每次必消毒，所以落盘的是：

```html
<line x1="40" y1="270" x2="360" y2="30" />
```

没有 `stroke` 的 `<line>` 等价于 `stroke:none` —— **线完全不显示**。学生看到的是一张白底 + 一堆字母与刻度数字的图，而**接口 200、数据库状态 done、前端正常显示**。

**这条极其恶劣的地方在于：所有测试都发现不了。** 因为没有任何测试去渲染它，而唯一碰到它的那条安全测试反而写的是
`assert "style" not in clean` —— **等于用一个测试把这个 bug 钉成了规范**。

**实测证据**（可复跑）：`python backups/_probe_svgstyle.py`

```
原始:   <line ... style="stroke:#333;stroke-width:2;fill:none"/>
消毒后: <line ... />                       ← 描边被删，线不可见
```

**修法**：`sanitize_style_attr()` —— 不再整条删，改为**按 CSS 属性白名单保留**
（stroke / stroke-width / stroke-dasharray / fill / font-* / marker-* / opacity 等），
危险构造（`http(s):`、`data:`、`javascript:`、`expression()`、`@import`、`behavior:`、`url()` 非内部引用）逐条丢弃。
同时把那条安全测试改成**按意图断言**：危险的去掉、安全的留下。

修复后实测：线段保住描边；`http://evil` / `expression(` / `@import` / `<script` / `background-image` 全部被剔除。

### 缺陷 B（已修）：计算器的单位与底数**没告诉模型**

`calc_service` 的 `sin/cos/tan` 走 `math.sin` 即**弧度制**，`log`/`ln` **都是自然对数**。
而工具 schema 只写"支持 sin/cos/tan、log/ln"，**不写单位、不写底数**；解题提示词同样没写。

后果：模型做初三几何题写 `sin(30)` 期望 0.5，实际拿到 **-0.9880316240928618**，
而这个错值会**直接进入给学生的解题步骤**。`log(100)` 同理得 4.605 而不是 2。

顺带发现：**同仓库有两套三角函数约定** —— `coord_engine.eval_expression` 服务于图纸坐标，用的是**度数制**（`sin(30)` 就是 0.5）。两处各自内部都对，但极易互相看齐改错。

**修法**：
1. schema 与解题提示词都写明单位与底数；
2. 新增 `radians` / `degrees` / `log10` / `lg`，让"写对"比"猜对"容易；
3. **让 `_SymbolExpr` 参数可用** —— 原先 `sin(pi/6)`、`sin(30*pi/180)` 直接报"函数 sin 暂不支持符号参数"，
   而它们恰恰是数学里最自然的写法。现在取符号对象的数值参与计算，结果仍是精确的 `1/2`。

修复后实测：`sin(pi/6)`→`1/2`、`sin(30*pi/180)`→`1/2`、`cos(pi/3)`→`1/2`、`tan(pi/4)`→`1`、`degrees(pi)`→`180`。

### 缺陷 C（已修）：分数吸附判据太松 → 把无理数当精确分数，且链式丢精度

`_format_result` 与 `_to_fraction` 都用 `limit_denominator(10000)` 且容差 `1e-9`：

- `log10(7) = 0.8450980400142568` 被改写成 **`431/510`**（误差 8e-10）—— 把一个**无理数**呈现成**精确分数**；
- 更糟的是**这个假分数会被后续计算继续使用**：`_eval_call` 里
  `nums = [_to_number(_to_fraction(a)) for a in args]` 会把**每个浮点参数**有理化，
  于是 `sin(radians(30))` 得到 `0.5000000385`、`degrees(asin(0.5))` 得到 `30.0000025`。

**修法**：判据改成"误差落在**浮点自身精度量级**内"（相对 `1e-12`，分母上限 1000），
两处共用同一套常量。修复后：`sin(radians(30))`→`1/2`、`degrees(asin(0.5))`→`30`（都变精确），
而 `0.1+0.2`→`3/10`、`1/3+1/7`→`10/21` 仍走精确分数路径（这是原本想要的行为）。

### 缺陷 D（已核实、未修）：`_validate_svg_quality` 是死代码

70 行的 SVG 质量校验（缺 viewBox、无绘图元素、非标准填充色、文字重叠、缺 `<defs>` 等），
**全仓库零调用点**（整仓 grep `validate_svg|svg_quality|check_svg|validate_diagram` 只命中定义行）。
`/api/diagram/check/{qid}/{index}` 只查**新鲜度**（时间戳），不查质量。

⇒ 生成的图**没有任何自动质量检查**。这也解释了缺陷 A 为什么能长期存在。
本轮先修 A（让学生至少能看到线）；**把 D 接进生成链路**留作下一步（需要先修它内部未受保护的 `float(v)`，见第四节）。
